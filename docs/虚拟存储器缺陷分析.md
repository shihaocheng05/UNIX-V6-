# 虚拟存储器缺陷分析与修复方案（修订版）

## 一、问题现象

| 现象 | 描述 |
|------|------|
| `ls` 命令正常 | 能正确列出目录内容，包括带参调用 |
| `echo`/`mkdir` 等命令失败 | 无有效输出，进程异常退出（`Exit: pid=2 sig=0`，stat=3） |
| 失败后 `ls` 也失效 | 出现 KPF（内核态缺页异常），输出 `KPF ebp=... ret=...` |
| 重启后 FATAL | 显示 `FATAL: No bootable device`，磁盘镜像损坏 |
| `ls` 能工作的原因 | `ls.exe` 的 TEXT/RDATA 段在 radix tree 中已有缓存（Shell 进程加载后遗留），后续缺页走缓存路径规避了缺陷 |
| `mkdir` 触发失败的原因 | `mkdir.exe` 是新 inode，从未在 radix tree 中缓存，TEXT 缺页走缺陷路径 |

## 二、根因分析

### 2.1 根因：第一次 `mkdir` Exit 时 inode 6493 数据块被污染

根据 `交接文档.md` 的核心结论：

> 文本段 ReadI 返回时第一字节为 `0x00000000`（非 x86 机器码）。该数据在第一次 mkdir exec 时尚为正常。**磁盘上 inode 6493 的数据块在第一次 mkdir Exit 路径中被污染**。

`交接文档.md` 建议的调试方法是：在 `IPut` 的 `FreeRangePage` 前后添加 Diagnose 输出，对比 `i_addr[]` 的值，确认 `FreeRangePage` 调用的 `kAllocator.FreeMemeory` 是否破坏了相邻的 Inode 表内存。

### 2.2 可能路径分析

**路径 A**：`FreeRangePage` → `kAllocator.FreeMemeory(sizeof(radix_tree_node), nodeAddr)` → 内核堆被破坏 → 影响 `m_Inode[]` 数组中的 `Inode` 对象 → 第二次 mkdir `ReadI` 时 `i_addr[]` 已损坏

**路径 B**：`Exit()` 中的 `FreePhyPage` 在释放 DATA/BSS/HEAP/STACK 时，写入了错误的物理地址 → 覆盖了文件系统的某个关键数据结构（如 Inode 缓存或 buffer cache）→ `Bmap` 算出的磁盘块号错误 → `ReadI` 读到垃圾数据

**路径 C**：`Exit()` 中释放栈段时 `sectionStartIdx` 计算错误 → 释放了错误的物理页 → 该物理页被后续分配并覆写 → 污染了某个被共享的数据结构

## 四、P1 bug 详细分析

### 4.1 【P1-BUG-1】selectVictim 第二轮无限循环

**位置**: `MemoryDescriptor.cpp` 第 369-393 行

```cpp
//找不到，找A==0的，总能找到
while(selected==NULL)
{
    current %= PageTable::ENTRY_CNT_PER_PAGETABLE;
    if(pAllocator->Page[userPageTableArray->m_Entrys[current].m_PageBaseAddress] > 1) // ← 缺陷
    {
        current++;
        continue;
    }
    if(userPageTableArray->m_Entrys[current].m_Used==1
       && userPageTableArray->m_Entrys[current].m_Present==1
       && userPageTableArray->m_Entrys[current].m_ReadWriter==1)
    {
        if(userPageTableArray->m_Entrys[current].m_Accessed==1)
        {
            userPageTableArray->m_Entrys[current].m_Accessed=0;
        }
        else
        {
            // 选中victim
        }
    }
    current++;
}
```

**问题**：当一个进程的所有 RW 私有页（`m_ReadWriter==1` 且 `m_Used==1` 且 `m_Present==1`）的 `Page[refcount]` 均 >1（被多个进程通过 COW 共享）时，`continue` 会跳过所有页，`current` 会一直递增到 1024 并取模后重新开始，形成**无限循环**。

虽然正常情况下 COW 后父进程和子进程都会将 PTE 改为 RO（`m_ReadWriter=false`），使得这些页不会被 `selectVictim` 考虑。但如果某处漏了改 RO，或者 DATA 段某个私有页从未触发过 COW（`m_ReadWriter` 一直是 1），就会触发此 bug。

**修复方案**：在此分支也加 `continue`，让 `current` 继续向后查找；或者改为在第一轮（`A==0 && D==0`）找不到时，清零所有 `Accessed` 位后重新扫描第一轮。

### 4.2 【P1-BUG-2】data 段 PTE==NULL 无缓存路径中加载后未改 RO

**位置**: `Exception.cpp` 第 417-441 行（DATA 段 `m_Used==0` 且无缓存分支）

**设计意图**：DATA 段从 inode 加载时，需要先读入文件内容。由于 ReadI 是写操作，PTE 必须先设为 RW。读入后，该物理页被挂入 radix tree 作为共享缓存（PTE 仍指向它）。后续进程访问同一页时，从 radix tree 取缓存，分配新的私有复制页。

**问题**：当前代码在读入后（第 416-441 行），**没有将 PTE 的 `m_ReadWriter` 改回 RO**，也没有设置 `m_Accessed`。该物理页在 radix tree 中被标记为共享（`Page[refcount]=1`），但 PTE 仍为 RW。这导致：

1. 该页在 fork 时被 `CopyUserPageTable` 的 `Page[refcount]++` 递增，但 `m_ReadWriter` 不会被修改（因为 `isText=false`）
2. 父进程写入该页 → 触发 COW → 从共享缓存复制 → COW 后双方 RW
3. 该页被 `selectVictim` 选为 victim 后换出，但该页是共享缓存，理论上不应被换出

**当前代码**（约第 416-441 行）：

```cpp
if(leaf_node->slot[...]==NULL)  // 该页没有缓存，需要从inode取
{
    unsigned long phyAddr = userPgMgr.AllocMemory();
    // ... 设置 PTE RW=1，读入 ...
    current->p_textp->x_iptr->ReadI();
    // 初始化 page 结构体并挂 radix tree
    leaf_node->slot[...] = sharedPage;
    leaf_node->count++;
}
// ← 缺失：未将 PTE 改为 RO！
// 当前 PTE 仍指向 RW=1 的页，后续 fork 会错误地 COW
```

**修复方案**：参考 TEXT/RDATA 段的处理方式（Exception.cpp 第 329-330 行），在 ReadI 之后、挂入 radix tree 之前，将 PTE 改回 RO：

```cpp
// ReadI 之后
userPageTableArray->m_Entrys[virtualIdx].m_ReadWriter = 0;  // 改回 RO
FlushPageDirectory(...);
// 然后挂 radix tree
leaf_node->slot[...] = sharedPage;
leaf_node->count++;
```

## 五、根因调查建议

根据 `交接文档.md`，真正的根因在第一次 `mkdir` Exit 时 inode 6493 数据块被污染。建议按以下步骤调查：

### 步骤 1：在 `IPut` 中添加诊断

在 `OpenFileManager.cpp` 第 220-223 行附近添加：

```cpp
Diagnose::Write("Before FreeRange: ino=%d slot=%x\n", pNode->i_index, userPgMgr.sharedPageRoot.slot[pNode->i_index]);
radix_tree_node::FreeRangePage(inode_layer_node);
Diagnose::Write("After FreeRange: ino=%d slot=%x\n", pNode->i_index, userPgMgr.sharedPageRoot.slot[pNode->i_index]);
Diagnose::Write("m_Inode[%d].i_addr[0]=%x\n", pNode->i_index, m_InodeTable->m_Inode[pNode->i_index].i_addr[0]);
```

### 步骤 2：在 `Exit` 的 DATA 段释放处添加诊断

在 `Process.cpp` 第 184-186 行附近添加：

```cpp
Diagnose::Write("Exit DATA free: startIdx=%x size=%x\n", dataVirtualIdx, u.u_MemoryDescriptor.m_DataSize);
// 调用 FreePhyPage 前后对比物理页框内容
```

### 步骤 3：在 `ReadI` 前后验证 inode 数据

在 `Exception.cpp` 第 312 行 ReadI 调用之后添加：

```cpp
Diagnose::Write("Post-ReadI inode=%d i_addr[0]=%x i_addr[1]=%x i_addr[2]=%x\n",
    current->p_textp->x_iptr->i_number,
    current->p_textp->x_iptr->i_addr[0],
```

```
├──────────┼────────────────┼────────────────────────────────── ┤
```

核心问题（P1-BUG-2）可能导致共享缓存页被污染，进而影响同一 inode 的其他进程。建议优先修复 P1-BUG-2，再通过调试输出确认 inode 污染的真正来源。
